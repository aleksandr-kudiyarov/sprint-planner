# Sprint Planner — Требования к системе

**Версия:** 1.1  
**Статус:** Draft (открытые вопросы закрыты)  
**Назначение:** Веб-приложение для оптимизированного распределения задач по разработчикам в рамках спринтов  
**Целевая команда:** 5–6 .NET/C# разработчиков  
**Принятие решений:** Tech Lead — финальный выбор плана спринта  

---

## 1. Контекст и цели

### 1.1 Проблема

При ручном планировании спринтов TL вынужден удерживать в голове одновременно:
компетенции каждого разработчика, его текущую загрузку, доступность, историческую
точность оценок, зависимости задач и приоритеты бизнеса. Это когнитивно затратно
и приводит к субоптимальным решениям, дисбалансу загрузки и накоплению технического долга
в распределении задач.

### 1.2 Цель системы

Система должна формализовать данные о задачах, разработчиках и истории спринтов,
запускать алгоритм оптимизации и предоставлять TL набор готовых вариантов плана
с явным описанием компромиссов — для осознанного выбора, а не замены человека.

### 1.3 Чем система не является

- Система **не заменяет** planning meeting и не принимает решения самостоятельно.
- Система **не является** трекером задач (не конкурирует с Jira/YouTrack).
- Система **не управляет** ходом спринта в реальном времени.

## 2. Роли пользователей

| Роль | Описание | Права |
|---|---|---|
| **Tech Lead** | Единственный пользователь системы в v1.0 | Полный доступ: настройка, запуск планировщика, выбор плана, ввод факт-данных |
| **Система** | Автономный агент оптимизации | Запись предложений планов, обновление статистики |

> Система используется только TL. Авторизация — одна роль, без ролевой матрицы.

## 3. Доменная модель

### 3.1 Сущности и атрибуты

**Developer (Разработчик)**
```
- id: UUID
- name: string
- email: string
- isActive: bool
- capacityHoursPerDay: decimal        // номинал, например 6 ч
- calendarOverrides: [{date, availableHours}]  // отпуск, встречи
- competencies: [DeveloperCompetency]
```

**Competency (Компетенция / Домен)**
```
- id: UUID
- name: string                        // "Kafka", "PostgreSQL", "API", "UI", "Auth", ...
- description: string
```

**DeveloperCompetency (Владение компетенцией)**
```
- developerId: UUID
- competencyId: UUID
- level: enum { None, Junior, Mid, Senior, Expert }
- levelNumeric: decimal               // 0.0 – 1.0, для расчётов
- lastUpdated: datetime
- updatedBy: string (TL)
```

**BacklogItem (Задача бэклога)**
```
- id: UUID
- externalId: string?                 // ссылочный ID из YouTrack (необязателен, только для удобства)
- title: string
- description: string
- type: enum { Feature, Bug, TechDebt, Review, Chore }
- priority: int                       // чем меньше — тем выше приоритет
- businessValue: decimal              // относительный вес ценности
- estimatedHours: decimal             // оценка в часах (единственная единица измерения)
- requiredCompetencies: [CompetencyRequirement]
- dependencies: [UUID]               // ID задач, которые должны войти в спринт раньше
- status: enum { New, ReadyForPlanning, InSprint, Done }
- preferredDeveloperId: UUID?         // continuity: предпочтительный исполнитель
- lockedDeveloperId: UUID?            // задача жёстко закреплена за разработчиком (Q5)
- lastDeveloperId: UUID?              // кто делал в прошлый раз
- tags: [string]
```

> **Решение по Q1:** Story Points исключены из модели. Единственная единица — часы.
> **Решение по Q5:** Поле `lockedDeveloperId` задаётся TL явно в карточке задачи.
> Солвер обрабатывает его как жёсткое ограничение: `x[locked_dev][j] = 1`.
> В UI drag & drop заблокирован для задач с `lockedDeveloperId`.

**CompetencyRequirement (Требование к задаче)**
```
- competencyId: UUID
- minimumLevel: enum { Junior, Mid, Senior, Expert }
```

**Sprint (Спринт)**
```
- id: UUID
- name: string
- startDate: date
- endDate: date
- status: enum { Planning, Active, Completed }
- goal: string
- selectedPlanId: UUID?
```

**SprintPlan (Вариант плана спринта)**
```
- id: UUID
- sprintId: UUID
- generatedAt: datetime
- isSelected: bool
- optimizationWeights: OptimizationWeights
- assignments: [TaskAssignment]
- metrics: PlanMetrics
```

**TaskAssignment (Назначение задачи)**
```
- taskId: UUID
- developerId: UUID
- estimatedHours: decimal
- continuityBonus: bool               // задача с тем же разработчиком, что и в прошлый раз
- skillFitScore: decimal              // 0.0 – 1.0
```

**PlanMetrics (Метрики плана)**
```
- totalBusinessValue: decimal
- capacityUtilization: {developerId -> decimal}  // % загрузки
- loadBalanceScore: decimal           // 1 - CV(загрузки)
- averageSkillFit: decimal
- riskScore: decimal                  // вероятность перегрузки хотя бы одного
- continuityScore: decimal            // доля задач с preferred developer
- criticalPathLength: decimal         // длина критического пути в часах
```

**OptimizationWeights (Веса критериев)**
```
- businessValue: decimal              // w1
- loadBalance: decimal                // w2
- skillFit: decimal                   // w3
- riskMinimization: decimal           // w4
- continuity: decimal                 // w5
- sum = 1.0 (нормализованы)
```

**SprintHistory (Факт выполнения спринта)**
```
- sprintId: UUID
- taskId: UUID
- developerId: UUID
- estimatedHours: decimal
- actualHours: decimal
- completedAt: datetime?
- wasCompleted: bool
- notes: string
```

## 4. Функциональные требования

### F1 — Управление справочниками

**F1.1 Управление разработчиками**
- TL может добавлять, редактировать, деактивировать разработчиков.
- Для каждого разработчика задаётся номинальная дневная ёмкость (capacity).
- Для каждого разработчика TL может ввести исключения по доступности на конкретные даты
  спринта (отпуск, выезды, сокращённые дни).
- Эффективный capacity на спринт рассчитывается автоматически как:
  `∑(доступные часы по каждому дню спринта)`.

**F1.2 Управление компетенциями (доменами)**
- TL ведёт справочник компетенций команды (Kafka, PostgreSQL, gRPC, Kubernetes, UI, Auth...).
- Для каждой пары разработчик–компетенция TL выставляет уровень владения
  (None / Junior / Mid / Senior / Expert).
- История изменений уровней сохраняется с датой и автором.

**F1.3 Управление задачами бэклога**
- TL может вручную добавлять и редактировать задачи.
- Для каждой задачи указываются: тип, приоритет, бизнес-ценность, **оценка в часах**,
  требуемые компетенции с минимальным уровнем, зависимости от других задач,
  preferred developer (continuity), locked developer (жёсткое закрепление).
- Поле `externalId` — необязательное текстовое поле для ссылки на задачу в YouTrack:
  удобно для поиска, но никакой синхронизации нет.
- Система автоматически запоминает, кто выполнял задачу в прошлый раз,
  и подставляет его как preferred developer для следующего спринта при необходимости.
- Зависимости задач валидируются на ацикличность (DAG).
- `lockedDeveloperId` можно задать или снять в любой момент. При наличии блокировки
  система предупреждает, если у разработчика нет нужной компетенции.

### F2 — Аналитика и статистика разработчиков

> **Решение по Q4 (cold start):** История спринтов на старте отсутствует.
> Система работает в режиме «начало с нуля»: все статистические параметры
> инициализируются консервативными значениями по умолчанию и накапливаются
> начиная с первого закрытого спринта. В UI явно отображается badge
> «Недостаточно данных — используется оценка по умолчанию» до накопления
> минимум 3 спринтов истории.

**F2.1 Velocity разработчика**
- Система рассчитывает индивидуальный velocity каждого разработчика
  (в часах) за последние N спринтов (N настраивается, по умолчанию 5).
- **Cold start:** до первого завершённого спринта velocity не отображается.
  Вместо него используется `capacityHoursPerDay × рабочие дни × 0.8`.
- Отображается: среднее, стандартное отклонение, тренд (растёт / падает / стабилен).

**F2.2 Точность оценок (коэффициент β)**
- Для каждого разработчика хранится и отображается коэффициент точности оценок:
  `β = среднее(фактические часы / оценка в часах)`.
- Разбивка по типам задач (баги оцениваются точнее, чем новые фичи?).
- При генерации плана система автоматически корректирует оценку:
  `скорректированные часы = estimatedHours × βi`.
- **Cold start:** при отсутствии истории `βi = 1.0` (без коррекции).
  Значение по умолчанию отображается в UI как «ещё нет данных».

**F2.3 Профиль компетенций в разрезе истории**
- Для каждой пары разработчик–компетенция: сколько задач выполнено, средняя точность оценок,
  средняя скорость. Позволяет со временем вручную уточнять `skillLevel`.
- **Cold start:** раздел отображается пустым с подсказкой «данные появятся после первого спринта».

**F2.4 Командный velocity**
- Суммарные часы, закрытые командой за последние N спринтов.
- Используется как ориентир при формировании бюджета спринта.
- **Cold start:** TL вручную задаёт целевой бюджет спринта в часах при первом планировании.

### F3 — Движок планирования (оптимизация)

**F3.1 Входные параметры сессии планирования**
- TL выбирает спринт (даты, цель).
- TL выбирает задачи из бэклога, допустимые к планированию (пре-фильтрация).
- TL задаёт веса критериев оптимизации через интуитивный слайдер
  (или выбирает из предустановленных профилей: «фокус на ценность», «фокус на стабильность»,
  «равномерная загрузка»).
- TL задаёт уровень риск-аппетита (0–100%), влияющий на параметр Γ робастной оптимизации.

**F3.2 Алгоритм оптимизации**
- Задача решается как задача целочисленного линейного программирования (ILP / MIP).
- Solver: Google OR-Tools (SCIP / CP-SAT backend).
- Целевая функция — взвешенная сумма критериев:
  ```
  max: w1×BusinessValue + w2×LoadBalance + w3×SkillFit + w4×(−Risk) + w5×Continuity
  ```
- Ограничения:
  - Каждая задача назначена не более чем одному разработчику.
  - Скорректированная суммарная нагрузка не превышает capacity с робастным буфером:
    `∑(βi × ej × xij) + Γ × ∑(σj × xij) ≤ capacityi`.
  - Назначение запрещено, если `developerSkillLevel < задача.minimumSkillLevel`.
  - Зависимости задач: задача B включается в спринт только если включена задача A.
  - **Locked constraint (Q5):** если у задачи задан `lockedDeveloperId`,
    то `x[lockedDev][j] = 1` — жёсткое равенство, не оптимизируется.
    Если у locked-разработчика не хватает capacity — солвер возвращает предупреждение,
    а не падает: задача включается с нарушением буфера, UI показывает предупреждение.
- **Cold start (Q4):** при отсутствии истории `βi = 1.0`, `σj = 0.3 × estimatedHours`.
- Solver ограничен по времени: не более 10 секунд на одну генерацию.

**F3.3 Генерация нескольких вариантов (Pareto-фронт)**
- По одной сессии система генерирует от 3 до 5 вариантов плана.
- Варианты отличаются точкой на парето-фронте: «максимум ценности», «минимум риска»,
  «баланс загрузки», промежуточные.
- Для каждого варианта рассчитываются и отображаются все метрики (F3.1).

**F3.4 Обработка неопределённости оценок**
- Система хранит для каждой задачи: `estimatedHours` и `σ (stddev)`,
  рассчитанный из истории аналогичных задач данного типа и компетенции.
- Если история отсутствует — σ задаётся как `0.3 × estimatedHours` по умолчанию.
- Вероятность перегрузки разработчика отображается явно как процент.

**F3.5 Критический путь**
- По графу зависимостей система вычисляет критический путь для каждого варианта плана.
- Задачи на критическом пути выделяются в UI.
- TL видит: какие задачи блокируют прогресс и кому они назначены.

### F4 — Интерфейс выбора плана (TL Decision Layer)

**F4.1 Обзор вариантов планов**
- Сравнительная таблица вариантов по всем метрикам.
- Radar chart (паучья диаграмма): визуальное сравнение по 5 критериям.
- Цветовое кодирование: зелёный / жёлтый / красный по уровню риска.

**F4.2 Детализация варианта плана**
- Список задач с назначенным разработчиком, оценкой, скорректированными часами,
  skill-fit score, флагом continuity, флагом критического пути.
- Доска по разработчикам: карточки задач, полоса загрузки с цветом (< 80% / 80–95% / > 95%).
- Предупреждения: конкретные риски (например: «Иванов перегружен с вероятностью 23%»,
  «Задача TASK-42 требует Expert Kafka, у назначенного — Mid»).

**F4.3 Ручная корректировка**
- TL может перетащить задачу на другого разработчика (drag & drop).
- После корректировки система немедленно пересчитывает метрики варианта.
- Если правка нарушает ограничение (навык, capacity) — система предупреждает,
  но **не блокирует** (TL принимает осознанное решение).
- **Locked-задачи (Q5):** перетаскивание заблокировано визуально и технически.
  Карточка задачи с `lockedDeveloperId` отображает иконку замка.
  TL может снять блокировку прямо из карточки — после чего drag & drop становится доступен.

**F4.4 Фиксация решения**
- TL выбирает вариант (с возможными ручными корректировками) и нажимает «Утвердить план».
- Утверждённый план фиксируется в БД как финальный план спринта.
- Остальные варианты сохраняются для истории и анализа.

---

### F5 — Фиксация факта и обратная связь

**F5.1 Ввод факт-данных по завершении спринта**
- TL по каждой задаче вводит: фактические часы, статус (выполнена / перенесена).
- Интерфейс должен быть быстрым: форма с предзаполненными оценками, только поле «факт».
- Перенесённые задачи автоматически возвращаются в бэклог.

**F5.2 Отчёт по спринту**
- После ввода факта: автоматический отчёт с отклонениями оценок по каждому разработчику,
  итоговый velocity команды и каждого, сравнение метрик выбранного плана с фактом.
- Обновление `βi` и `σj` на основе новых данных.

---

### F6 — Конфигурация и настройки

**F6.1 Профили весов оптимизации**
- TL может создавать, сохранять и переиспользовать именованные профили весов.
- Предустановленные профили:
  - «Ценность» (w1=0.5, w2=0.1, w3=0.2, w4=0.1, w5=0.1)
  - «Стабильность» (w1=0.2, w2=0.2, w3=0.2, w4=0.3, w5=0.1)
  - «Баланс» (w1=0.2, w2=0.3, w3=0.2, w4=0.2, w5=0.1)

**F6.2 Глобальные параметры**
- Длина спринта по умолчанию (в рабочих днях).
- Эффективный коэффициент рабочего времени (например, 0.8 — 80% времени на задачи).
- Количество спринтов для расчёта скользящего velocity (N, по умолчанию 5).
- Порог предупреждения по загрузке (по умолчанию 85%).

## 5. Нефункциональные требования

### 5.1 Производительность

| Операция | Требование |
|---|---|
| Генерация 5 вариантов плана | ≤ 30 секунд (для команды ≤ 10 чел. и ≤ 100 задач) |
| Пересчёт метрик после ручной правки | ≤ 1 секунда |
| Загрузка любой страницы UI | ≤ 2 секунды (p95) |
| Сохранение решения | ≤ 500 мс |

### 5.2 Надёжность
- Планировщик должен завершаться с лучшим найденным решением даже при timeout солвера.
- Все пользовательские действия (выбор плана, ввод факта) должны быть атомарными транзакциями.
- В случае ошибки солвера — информативное сообщение с возможностью повторного запуска.

### 5.3 Безопасность
- Аутентификация через Keycloak (JWT, OIDC).
- **Одна роль в v1.0** — TL. Ролевая матрица не нужна, все эндпоинты
  доступны любому аутентифицированному пользователю.
- Все API-эндпоинты защищены — без валидного JWT недоступны.
- Конфиденциальные данные (данные команды) не покидают инфраструктуру.
- В v2.0 при добавлении роли Developer потребуется ролевая авторизация
  на уровне эндпоинтов (row-level security по developerId).

### 5.4 Технический стек (ограничения)
- Backend: **ASP.NET Core 8** (.NET 8), C#.
- База данных: **PostgreSQL** (EF Core или Dapper).
- Оптимизационный движок: **Google OR-Tools** (NuGet: Google.OrTools).
- Frontend: **React + TypeScript** (или Blazor — на усмотрение, но React предпочтительнее
  для независимости от .NET releases).
- Контейнеризация: **Docker**, деплой в **Kubernetes** / Helm.
- Аутентификация: **Keycloak**.
- Логирование/мониторинг: **Prometheus + Grafana** (метрики latency солвера, endpoint latency).

### 5.5 Наблюдаемость
- Время выполнения оптимизации логируется и экспортируется как Prometheus gauge.
- Каждая сессия планирования создаёт structured log-запись с параметрами и метриками итога.
- Health check эндпоинт (`/healthz`) для Kubernetes liveness/readiness probe.

### 5.6 Масштабируемость (ограничения области применения)
- Система рассчитана на команду 3–15 разработчиков и бэклог ≤ 500 задач.
- Горизонтальное масштабирование не требуется (single-instance достаточно).

## 6. Ограничения и явные исключения (Out of Scope v1.0)

| Тема | Решение |
|---|---|
| Интеграция с YouTrack / Jira | Нет ни в v1.0, ни в v1.1. Ручной ввод — осознанное решение. `externalId` — просто текстовое поле для справки |
| Уведомления разработчикам | Нет. TL сам коммуницирует итоги |
| Мобильный интерфейс | Нет. Только desktop-браузер |
| Парная разработка (2 dev на задачу) | Нет. Одна задача = один исполнитель |
| Реалтайм-трекинг прогресса спринта | Нет. Только планирование и постфактум |
| Автоматическое обновление компетенций | Нет. Только ручное обновление TL |
| Мультикомандный режим | Нет. Одна команда на инстанс |

## 7. Критерии приёмки системы

### 7.1 Корректность оптимизации
- На тестовом наборе из 30 задач / 5 разработчиков ни один из предложенных планов
  не нарушает capacity-ограничений.
- Задачи с неудовлетворёнными skill-ограничениями не назначаются.
- Задачи с неудовлетворёнными зависимостями не включаются в план.

### 7.2 Качество предложений
- Суммарный business value предложенных планов не хуже жадной эвристики более чем на 5%.
- Дисбаланс загрузки (макс. разброс между разработчиками) ≤ 20% capacity.

### 7.3 Пользовательский сценарий (E2E)
TL может пройти полный сценарий за ≤ 15 минут:
1. Открыть приложение → 2. Создать новый спринт →
3. Отметить задачи для планирования → 4. Запустить оптимизацию →
5. Сравнить варианты → 6. Скорректировать вручную →
7. Утвердить план → 8. Экспортировать или передать команде.
